    テンプレート .dotx、~$ で始まる .docx 取り込み対象にならない インデックス作成
    インデックス作成後の Word・PowerPoint プロセス 残らない（利用者が使用中の Word には触れない） インデックス作成

    6.3 テストの構成と実行¶

    テストは scripts/ と同じ構成に並べる。どのモジュールのテストがどこにあるか、たどらなくても分かるようにするため。

    フォルダ 内容
    tests/helpers/ 共通の準備（load.ps1。$here・${scriptsDir} を決めて tebunko_grep/lib.ps1 を読み込む）とテスト用の TSV 作成（tsv.ps1）
    tests/shared/core/ fs・text・folder・settings
    tests/shared/office/ office_files・office_process・office_reader・office_app
    tests/tebunko_grep/core/ settings（setting.config）
    tests/tebunko_grep/index/ index_name・index_store
    tests/tebunko_grep/indexer/ indexer_state・indexer_decide・indexer_plan・extract_office
    tests/tebunko_grep/search/ search_query・search_run・source_map
    tests/tebunko_grep/ui/ 画面の判断層（index_view・indexing_view・search_view・preview_view）
    tests/meta/ 構成を守るテスト（structure・encoding・layers）と安全性の検査（safety）
    tests/testdata/ 手動の結合テスト用のデータ（6.2）と、その生成・個人情報の除去（scrub_personal）

    tests/meta/ は、直し忘れると気づきにくい決まりごとを機械的に確かめる。

    テスト 確かめること
    structure $rootDir などのパス定義、全 .ps1 の構文、Add-Type -TypeDefinition を使わない、XAML が XML として読める・x:Name がある、型を読み込む順で継承が解決できる
    encoding 全 .ps1・.xaml が BOM 付き UTF-8 で、改行が CRLF
    layers shared/ にツールの名前が出てこない、ツール同士が互いを読み込まない、起動口からたどれない .ps1 が無い、判断層に画面への依存が無い
    safety 危険な処理を使っていない、Office をマクロ無効・読み取り専用で開く、原本を書き換えない、書き込み先が work・%TEMP% だけ、PSScriptAnalyzer の指摘が 0 件、審査用の資料がそろっている（04_安全性.md）

    タグと実行¶

    Describe にタグを付け、実行するものを選べるようにする。

    タグ 内容 外部ソフト
    Unit 判断層（入力は素の値、出力は素の値） 不要
    Io ファイルの読み書き（$TestDrive の中で完結する） 不要
    Meta 構成を守るテスト 不要
    Office Excel・Word・PowerPoint の COM を実際に動かすもの 必要
    Slow 時間のかかるもの 不要

    実行は tests/run.ps1 から行う。

    .\tests\run.ps1              既定（Unit・Io・Meta。Office と Slow は外す）
.\tests\run.ps1 -Tag Unit    速い確認だけ
.\tests\run.ps1 -All         Office・Slow も含める（Office が必要）
.\tests\run.ps1 -Ci          結果の XML（work\test\results.xml）とカバレッジ（work\test\coverage.xml）を出す
.\tests\run.ps1 -Path .\tests\shared\core   指定したフォルダ・ファイルのテストだけ

    いずれも失敗したテストの数を終了コードにする（pre-commit フックと CI が見る）。1 件も実行しなかったときも失敗にする（終了コード 1）。タグの打ち間違いで、何も確かめないまま通るのを防ぐため。

    -Tag・-ExcludeTag はカンマ区切りの文字列でも受け取る。powershell.exe -File で呼ぶと -Tag Unit,Meta は配列にならず 1 つの文字列で渡るため（pre-commit フックがこの呼び方）。tests/meta/runner.Tests.ps1 が、この呼び方で 0 件なら失敗になることと、タグを分けて受け取ることを確かめる。

    カバレッジは判断層・状態層だけを対象にする（画面層 gui.ps1・*_tab.ps1・shell.ps1・app_host.ps1・*_dialog.ps1 は自動テストの対象外のため）。 下限は tests/coverage.baseline に置き、下回ると -Ci が失敗する。上がったら基準を上げる。

    -Ci はカバレッジを Cobertura 形式の XML（work\test\coverage.xml）にも書き出す。Pester 3.4 はカバレッジをファイルに出せないため、tests/run.ps1 が結果（コマンド単位）から行単位に組み立てる。1 行に実行されたコマンドが 1 つでもあれば、その行は通ったものとする。そのため、行単位の値はコマンド単位の値と少し違う。ファイル名はリポジトリからの相対パスで書き、利用者名を含む絶対パスは入れない。

    CI¶

    .github/workflows/test.yml で、push と pull request のたびに windows ランナーで実行する。

    • Windows PowerShell 5.1 はランナーに最初から入っている（shell: powershell を明示する。pwsh（PowerShell 7）では COM と文字コードの扱いが変わる）
    • ランナーには Pester 5 も入っており、そのままでは Invoke-Pester が 5 を読み込んで全テストが失敗する（5 はテストの書き方が違う）。tests/run.ps1 は Import-Module Pester -MaximumVersion 3.99.99 で 3 系を明示し、CI は 3 系が無ければ 3.4.0 を入れる
    • スクリプトの改行はランナーの core.autocrlf に左右されないよう、.gitattributes で .ps1・.xaml・.bat を CRLF に固定している
    • ランナーに Office は入っていないため、タグ Office のテストは自動的に外れる。COM を使うインデックス作成の確認は手元で -All を使う（6.2）
    • あわせて PSScriptAnalyzer の Error を 0 件に保つ（継承元が別ファイルのための TypeNotFound は除く）。PSScriptAnalyzer の版は test.yml で固定する（新しい版でルールが増えて、コードを変えずに CI が落ちるのを防ぐ。Dependabot の対象外のため、上げるときは版を書き換えた PR で指摘が 0 件のままか確かめる）。安全性の検査（tests/meta/safety.Tests.ps1）はタグ Meta のため既定で実行され、PSScriptAnalyzer が入っていない環境では静的解析の項目だけを飛ばす
    • テストの前に tools/check_commit.ps1 で、追跡している全ファイルと全コミットの作者を検査する（下の「公開してはいけない内容の検査」）。作者を全履歴で調べるため fetch-depth: 0 で取得する
    • 同じブランチに続けて push したときは、古い実行を取り消す（concurrency）
    • テストのあと、work\test\coverage.xml を Codecov に送る（codecov/codecov-action。版はコミットのハッシュで固定する）。README のバッジ、PR へのコメント（ファイルごとの増減）、行ごとの表示は Codecov が出す
    • 送るのは相対パスと行ごとの実行回数だけで、ソースは送らない（Codecov はソースを GitHub から読む）
    • トークンはリポジトリの Secrets の CODECOV_TOKEN に置く。fork からの PR ではトークンが無くても送れる
    • 送れなくても CI は失敗にしない。Codecov の判定（.github/codecov.yml）も参考表示だけにする。下限の確認は tests/coverage.baseline が受け持つ
    • .github/codecov.yml には ASCII の文字だけを書き、コメントも書かない。Windows で動く Codecov の CLI がこのファイルを cp1252 として読み、日本語があると UnicodeDecodeError で止まるため。tests/meta/encoding.Tests.ps1 が確かめる
    • タグの push（release.yml から呼ばれたとき）では送らない

    ほかに、サプライチェーンの安全性のために次のワークフローを置く。どちらも main へのマージは止めない。

    • .github/workflows/codeql.yml … GitHub Actions のワークフローを CodeQL で解析し、Security タブ（Code scanning）に載せる。信頼できない入力を run に埋め込む書き方などを見つける。PowerShell は CodeQL の対象外のため、スクリプトは上の PSScriptAnalyzer が受け持つ
    • .github/workflows/scorecard.yml … OpenSSF Scorecard で採点し、結果を Code scanning と README のバッジに載せる。main への push・ブランチ保護の変更・毎週 1 回で動く
    • 使うアクションは、どのワークフローでもコミットのハッシュで固定する（採点の項目 Pinned-Dependencies。版はハッシュの後ろのコメントに書き、Dependabot が更新する）
    • Scorecard はリポジトリを Linux で展開する。名前が UTF-8 で 255 バイト（日本語で 85 字）を超えるファイルがあると展開できず、ほとんどの項目が採点できなくなる。そのため tools/check_commit.ps1 がこの長さを超える名前を止める

    v で始まるタグを push すると .github/workflows/release.yml が動き、test.yml と同じ検査・テストを通したうえで、tools/new_release_package.ps1 で配布 zip（tebunko_grep-<タグ>.zip）を作って GitHub Release に載せる。zip にはカタログ（tebunko.cat）とハッシュ一覧（SHA256SUMS.txt）を同梱し（04_安全性.md の 5.1）、zip 自体の SHA256 をリリースの説明に書く（同 5.6 の VirusTotal での照会用）。あわせて zip のビルドの来歴を Sigstore で署名して GitHub に登録し、署名の bundle（tebunko_grep-<タグ>.zip.sigstore.json）もリリースに載せる（同 5.1）。

    git tag v1.0.0
git push origin v1.0.0

    設計書（docs/）は .github/workflows/docs.yml が MkDocs（テーマは Material for MkDocs）で Web サイトにし、main が更新されるたびに GitHub Pages に公開する。

    • 設定は tools/mkdocs/mkdocs.yml。サイトはどれもリポジトリの直下で mkdocs build --strict -f tools/mkdocs/mkdocs.yml を実行して作る。リンク先のファイルや見出し（アンカー）が無いと失敗する
    • GitHub Pages は gh-pages ブランチの内容をそのまま公開する。main のサイトはその直下に置く
    • docs/・tools/mkdocs/ を変えた PR では、サイトのプレビューを gh-pages の pr-preview/pr-<PR の番号>/ に置き、URL を PR にコメントする（rossjrw/pr-preview-action）。push のたびに更新し、PR を閉じたら消す。fork からの PR ではプレビューを作らず、サイトを作れることだけを確かめる
    • サイトを作るジョブは PR のコード（tools/mkdocs/hooks.py）を動かすため、読み取りの権限だけで動かす。gh-pages への書き込みと PR へのコメントは、作ったサイトを受け取るだけの別のジョブで行う
    • アンカーは GitHub と同じ形（日本語を残し、記号を除き、英字を小文字にする）で作る（tools/mkdocs/mkdocs.yml の toc.slugify）。docs/ の中のリンクは GitHub で読めるように書けば、サイトでもそのまま飛べる
    • GitHub で読むときとの違いは tools/mkdocs/hooks.py で埋める。00_index.md をサイトの先頭ページにし、docs/ の外（../.github/SECURITY.md など）へのリンクは GitHub 上のファイルへのリンクに書き換える
    • 使うパッケージは tools/mkdocs/requirements.txt に版とハッシュで固定し、pip install --require-hashes で入れる。更新は Dependabot が PR を出す。サイトを作るときだけに使い、配布物には含めない
    • サイトを見る人のブラウザーが第三者のサーバーへ通信しないようにする。フォントは Google Fonts を使わず OS のもので表示する（theme.font: false）。Mermaid は Material テーマが既定では unpkg から読み込むため、extra_javascript で版を固定して先に読み込ませ、privacy プラグインがビルドのときに取り込んでサイトに同梱する（取り込んだファイルは work/cache/privacy/ に置く）。Mermaid の版は、Material テーマが読み込む版（mermaid@11）に合わせる
    • 手元で見るときは次のとおり（生成物は work/site/）
    pip install --require-hashes -r tools/mkdocs/requirements.txt
mkdocs serve -f tools/mkdocs/mkdocs.yml

    コミット前の検査（pre-commit フック）¶

    clone したら 1 回だけ次を実行する。core.hooksPath を tools/hooks にし、コミットのたびに tools/hooks/pre-commit が動く（git worktree で作ったツリーでも、そのツリーのフックが動く）。

    .\tools\install_hooks.ps1              有効にする
.\tools\install_hooks.ps1 -Uninstall   やめる
    順 内容 所要時間の目安
    1 tools/check_commit.ps1 -Staged：ステージした内容と、これから作るコミットの作者を検査する 数秒
    2 tests/run.ps1 -Tag Unit,Meta -Quiet：速いテスト（Io を含む既定のテストと静的解析は CI で行う）。失敗したテストだけを表示する 1 分強

    どうしても飛ばすときは git commit --no-verify。CI で同じ検査が走る。フックは git for Windows の sh が読むため LF で保存する（.gitattributes で固定）。

    公開してはいけない内容の検査（tools/check_commit.ps1）¶

    リポジトリは公開しているため、履歴に一度でも入れたら公開されたのと同じになる（AGENTS.md「個人情報を書かない」）。これを機械的に止める。

    対象 見つけたら失敗にするもの 例示用として通すもの
    絶対パス C:\Users\<名前>（/ 区切り・\\ のエスケープも） test（test_ のように長さを揃えたものも）・a・Public・%USERNAME% <利用者名> のような置き換え用の表記
    メールアドレス すべて example.com などの例示用のドメイン、GitHub の noreply
    Office ファイル 作成者・最終更新者（docProps/core.xml・ODF の meta.xml・PDF の /Author）、コメント・変更履歴の作成者に付くアカウント ID（userId） test、空、0 だけの ID
    手元で実行したとき Windows のユーザー名そのもの（CI では調べない） —
    .ps1・.xaml BOM 付き UTF-8 でない、改行が CRLF でない —
    コミットの作者・コミッター GitHub の noreply 以外のメールアドレス noreply@github.com（GitHub 上でマージしたときのコミッター）

    Office ファイル（ZIP）は展開して中の XML・バイナリを 1 つずつ調べる。旧形式（.doc .xls .ppt）・PDF などはバイト列を UTF-8 と UTF-16LE の両方で読んで調べる。中身は作業ツリーではなく git に記録される内容を読む（改行だけは、git が LF にして記録するため作業ツリーのファイルで調べる）。
