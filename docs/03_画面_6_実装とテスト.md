### 12.1 待たせ方の方針（画面を固まらせない）

**画面が「応答なし」になることは、処理が長いこと自体よりも利用者を不安にさせる**（壊れたと思って強制終了され、インデックス作成が中断して Office のプロセスが残る）。そのため、次を守る。

| 方針 | 具体 |
|---|---|
| **画面のスレッドで 0.2 秒を超える可能性のある処理をしない** | ファイル数・行数に比例する処理（取り込み一覧の集計、インデックスの削除、TSV の数え上げ）は Runspace（`startJob`）で行い、終わったら画面のスレッドで結果を反映する。終わるまでは、その操作のボタンを無効にして何をしているかをステータスに出す |
| **繰り返し読むものは小さくする** | 1 秒ごとに読むものは「進み具合の 1 行」（`work/インデックス作成進捗.txt`）にする。数万行の取り込み一覧を毎秒読み直すと、その間ずっと画面が止まる（5 万行で 1 回約 5.8 秒）。書く側（インデクサ）が数えて 1 行にする |
| **無言の時間を作らない** | 待ちが数秒を超えうる場所では「何をしているか」を必ず出す（`クロールしています…` ＋ 今見ているフォルダ、`インデックス作成を終えています…` ＋ 今の後片付け、`検索対象のファイルを確認しています…（N 件）`、`インデックス […] の TSV を削除しています…`）。件数が増えるのが見えれば、止まっていないと分かる |
| **長い処理は止められるようにする** | インデックス作成は［中止］（ファイルの切れ目で止まる・続きから再開できる）、検索は［中止］（それまでの結果は残す） |
| **終わったことを知らせる** | インデックス作成が終わったとき、進み具合とステータスで知らせる（以前はタスクバーのボタンを光らせていたが、P/Invoke（`FlashWindowEx`）を無くすため廃止した） |

数万件規模での実測（この方針の根拠。1 万ファイル ≒ TSV 2 万件 / 取り込み一覧 1 万行、5 万ファイルは 5 万行）:

| 処理 | 1 万 | 5 万 | 対応 |
|---|---|---|---|
| 取り込み一覧の読み込み（`readStatusFile`） | 1.2 秒 → 0.32 秒 | 5.8 秒 → 1.4 秒 | 1 行ごとの関数呼び出しをやめた。**毎秒の読み直しも廃止**（進み具合の 1 行を読む。実測 約 1 ミリ秒） |
| 取り込み一覧の書き出し（`writeStatusFile`） | 3.1 秒 → 0.08 秒 | 17.0 秒 → 0.22 秒 | 1 行ごとの関数呼び出し・パイプラインをやめた（インデックス作成の開始・終了時の無言の待ちが短くなる） |
| 状態の集計（`getIndexingState`） | 2.3 秒 → 0.91 秒 | 15.5 秒 → 5.3 秒 | 別スレッドへ（`refreshIndexingState`）。日時の解析も、必要なときだけ行う |
| 検索対象の数え上げ（`getIndexTsvFiles`） | 6.0 秒 → 2.2 秒（TSV 2 万件） | – | .NET の列挙に変更。検索スレッドで行い、途中の件数を表示する |
| インデックスの削除 | 6.7 秒（1 万フォルダ） | – | 別スレッドへ（削除中は操作を止めてステータスに出す） |

（測定: Windows PowerShell 5.1・ローカルディスク。1 万 = 元ファイル 1 万件（取り込み一覧 1 万行・TSV 2 万件）、5 万 = 取り込み一覧 5 万行）

> PowerShell 5.1 では**関数呼び出しが 1 回あたり約 50 マイクロ秒**かかる。5 万行で 1 行 1 回呼ぶと、それだけで約 2.7 秒になる。数万件を回すところでは、関数呼び出し・パイプライン（`ForEach-Object` / `Where-Object`）・`$obj.$名前` の動的アクセスを避ける（普通の場所では読みやすさを優先してよい）。

別スレッドの扱い：

- 検索・TSV の件数取得・取り込み一覧の集計・インデックスの削除は Runspace（`startJob`）で実行する。検索結果はスレッド間で共有するキュー（`ConcurrentQueue`）に入れ、画面の `DispatcherTimer`（0.1 秒間隔）で取り出して表に加える。中止はフラグで伝える。同じ集計が重ならないよう、実行中なら「もう一度」の印だけを立てて、終わってからやり直す。
- インデックス作成のプロセスは `Start-Process -PassThru`（ウィンドウなし）で起動し、`DispatcherTimer`（1 秒間隔）で `HasExited` と進み具合の 1 行（`work/インデックス作成進捗.txt`）を確認する（3.6）。終了後は `ExitCode` で表示を分ける（3.7）。起動時と開始時は、`Win32_Process` のコマンドラインから実行中のインデックス作成を探し、見つかればそのプロセスを監視する（3.3）。
- 進み具合の段階が `確認` になったら、インデックス作成の確認ダイアログを開く（3.4）。**ダイアログを開いている間も `DispatcherTimer` は動く**（`ShowDialog` は入れ子のメッセージループのため）。開く前に「開いた」ことにして、二重に開かないようにする。
- 多重起動は、ツールの配置フォルダごとの名前付き Mutex（`Local\tebunko_gui_<フォルダのハッシュ>`。ハッシュは `getFolderKey`）で防ぐ。2 つ目のプロセスは、同じくフォルダごとの名前付きイベント（`Local\tebunko_gui_activate_<フォルダのハッシュ>`）を合図して終了し、すでに開いている画面が `DispatcherTimer`（0.3 秒間隔）でそれを確認して `Window.Activate()`（＋最小化なら復帰）で前面に出す。※以前は C# の P/Invoke（`AttachThreadInput`＋`SetForegroundWindow`）で確実に前面を奪っていたが、実行時コンパイルを無くすため廃止した。別アプリが前面のときはフォーカスを奪えないことがある（OS の制限）。

注意（PowerShell 5.1）：`System.Collections.Generic.List[object]` を `@()` で配列にする・`[object[]]` 引数に渡すと例外（Argument types do not match）になる。結果のリストは `List[psobject]` にするか `.ToArray()` で返す。また PS class のメソッド内では、クラスのプロパティと同じ名前（大文字小文字を区別しない）のローカル変数は使えない（`$this.` の付け忘れとみなされる）ため、別名にする。

### 12.2 実行時コンパイル（csc.exe）を使わない

資産管理・EDR は「`powershell.exe` が `csc.exe` を起動して `%TEMP%` の一時 DLL を読み込む」動き（実行時コンパイル。MITRE ATT&CK T1027.004）を、良性でも拾うことがある。tebunko はこれを一切出さない設計にする。

- **画面で使う型は PowerShell class**（`HitRow`・`Segment`・`PreviewColumn`／`Cell`／`Row`／`Table`・`ProcRow`・`FailRow`・`PlanRow`・`FolderItem`・`SearchTarget`・`SearchExclude`・`IndexNode`・`FolderNode`・`FolderEntry`）。PS class はエンジンがメモリ内で用意し、`csc.exe`・一時 DLL を出さない。`INotifyPropertyChanged` は `NotifyBase` を継承して実装する。
- **検索・TSV 読み取りは .NET を直接呼ぶ**（`tebunko_grep/lib.ps1` の `searchTsvFiles`／`newTsvFiles`／`readTsvContext`。`StreamReader`＋`[regex]`）。
- **Win32/COM 連携（P/Invoke）を使わない**。フォルダ選択は**エクスプローラー風の自作ダイアログ**（WPF。[3.2.1](03_画面_1_インデックス管理タブ.md#321-フォルダ選択ダイアログ参照)。Windows 標準の `FolderBrowserDialog` はツリーだけで中身が見えず使いにくく、エクスプローラー形式の `IFileOpenDialog` は COM のインターフェース定義＝実行時コンパイルが要るため）、ドライブの列挙は `System.IO.DriveInfo`、ネットワークドライブの割り当て解決は CIM（`Win32_LogicalDisk`）、多重起動の前面化は `Window.Activate`、タスクバー・タイトルバーのアイコンは `Window.Icon`。以前使っていた `IFileOpenDialog`・`QueryDosDevice`・`SetForegroundWindow`／`AttachThreadInput`・`FlashWindowEx`・`SetCurrentProcessExplicitAppUserModelID` は廃止した。
- 結果、起動〜検索を通じて `Add-Type`（実行時コンパイル）は 0 回、`csc.exe` の起動・一時 DLL の生成も 0（実起動で確認）。読み込むのは Microsoft 署名済みの GAC アセンブリ（WPF・WinForms）だけ。
- 代償と対処：PS class はメソッド呼び出しが C# より遅い（実測: 検索コアは C# の約 2.6 倍だが 50 万行で約 0.6 秒。結果行 `HitRow` の一括生成は 1 万件で約 10 秒と遅いため、**可視行だけ作る遅延描画**（`HitRow.Prepare`＋`LoadingRow`。軽量生成は 1 万件で約 0.56 秒）で回避する）。また PS class はプロパティのセッターにロジックを書けないため、列幅・チェック・選択は `Set*` メソッドやイベントで変える。`subst` ドライブの解決は使えなくなる（フォルダ選択は自作ダイアログのため、パスの貼り付け・ドラッグ＆ドロップは使える）。
