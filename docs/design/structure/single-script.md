# 単一ファイル化の検討

扱うこと: `scripts/` を展開せずに 1 本の `.ps1` のまま動かせるかどうかの検討（使い捨ての試作で確かめた結果と、進めるかどうかの結論）。扱わないこと: 配布物の現状のフォルダ構成そのもの（[配布物と開発用のフォルダ構成](folders.md)）、別の配布の形の案（自己展開型）の作り込み（下の「自己展開型との比べ」で考え方だけを比べる）。先に読むページ: [配布物と開発用のフォルダ構成](folders.md)。

今の配布は、`scripts/` 配下の多数の `.ps1`・`.xaml` を zip に入れ、`tebunko.bat`／インストーラーが `gui.ps1` を dot-source の連鎖で読み込む形。展開せずに動く 1 本の `.ps1` でも同じ役割分担を再現できるかを、使い捨ての試作で確かめた。結合ツール・生成した試作ファイル・計測の道具はすべて使い捨てで、このリポジトリには入れていない（実装した結合の道具は `tools/new_single_script.ps1`。[配布物と開発用のフォルダ構成](folders.md) を参照）。

6 つの関門（G1 構文と型・G2 別スレッド・G3 速さ・G4 安全性の検査・G5 Defender・G6 実行のしかた）を順に確かめた。結果は下の「試作の結果」にまとめる。

## パスに頼っている所

1 本化すると、元の「`scripts/shared/core/` 配下にこのファイルがある」という階層構造を前提にした箇所が壊れる。計画で挙げた P1〜P9 のそれぞれについて、試作で決めた置き換え方を次にまとめる。

- **P1 読み込み口の dot-source**（`gui.ps1`・`lib.ps1`・`shared/shared.ps1`・`indexer.ps1`・`indexer/indexer_lib.ps1` の `$PSScriptRoot\...` 経由の読み込み）: 結合ツールが、`tests/meta/layers.Tests.ps1` と同じたどり方で読み込みの順を追い、その順番どおりに連結する。
- **P2 別スレッドがパスで読む箇所**（`search_service.ps1` の `$libPath`・`gui.ps1` の `BackgroundQueue`・`indexer/indexer_run.ps1` の取り込みワーカースレッド・`indexer/indexing_session.ps1` の `& $indexerPath`）: 試作では、結合した `.ps1` 自身を `-Part <lib|indexerLib|indexer>` の引数つきで自己 dot-source する形にした（`[ScriptBlock]::Create` は G4 の禁止パターンに触れるため選ばなかった）。この方式は、**内部で自分自身を dot-source する箇所が増えるたびに、結合ツール側の書き換えが追従し続けなければならない**という構造的な弱さを持つ。書き換えが漏れると、分かりやすい実行時エラーになる場合も、応答がないまま止まる（ハング）という気付きにくい壊れ方になる場合もある。この弱さは、実装（段階 1〜3）では「別スレッドは単一 .ps1 そのものを自己 dot-source せず、読み込み口と同じ範囲（`lib`・`indexerLib`）のコードだけを文字列として持ち、`AddScript` で読む」という形に設計を改め、解消した（詳細は [クラスとランスペースの決まり](classes.md)・[スレッドの決まり](threads.md)）。
- **P3 XAML のリソース（テーマ）**: 元は 9 つの XAML がそれぞれ静的に `<ResourceDictionary.MergedDictionaries>` の中で `<ResourceDictionary Source="../../shared/xaml/theme.xaml" />` という相対パスで `theme.xaml` を読む形（例 `tebunko.xaml:18`）。試作では、この相対パスの `Source` 参照を外し、XAML は文字列として結合ファイルに埋め込み、`theme.xaml` の中身はコードで 1 回読み込んで `MergedDictionaries` に足す方式にした。
- **P4 アイコン**（`tebunko.ico` をファイルの `Uri` から読む）: `FromBase64String` が G4 の禁止パターンのため使えず、試作ではアイコンのバイト列（53491 バイト）をそのまま `[byte[]]@(整数, 整数, ...)` というリテラル配列としてファイルの先頭部分に埋め込み、実行時に `MemoryStream` 経由で `BitmapFrame::Create` に渡す形にした。結合後のファイルでこのリテラルが実際に占める分量は、この 1 行だけで約 185KB（189,766 バイト）あり、結合ファイルがその分だけ膨らむというトレードオフがある。
- **P5 作業の基準・データの置き場など**: `$rootDir`（`scripts/shared/core/paths.ps1` が `$PSScriptRoot` から 3 階層上がってリポジトリ直下を得ている箇所）は、`.ps1` ファイル自身の場所から計算し直す書き換えで対応した。データの置き場（`getDataDir`）・多重起動の判定に使う鍵（`getFolderKey`）・`VERSION.txt` の読み込みは `.ps1` の隣を基準にする形のまま動く。これらを `.ps1` の隣に作ってよいかという設計判断は、メンテナの答えにより「zip 版と同じ作り（`getDataDir` に任せ、書き込めないときだけ `%LOCALAPPDATA%` に逃げる）」に決まった。
- **P6 起動口 `tebunko.bat` の役割**: `tebunko.bat` は `scripts\` 配下に `Unblock-File` を再帰的にかけたあと、`conhost.exe` 経由で `powershell.exe -NoProfile -STA -ExecutionPolicy RemoteSigned -WindowStyle Hidden -Command "..."` として起動し、失敗したときは `$ExecutionContext.SessionState.LanguageMode`・`$PSVersionTable.PSVersion`・`Get-ExecutionPolicy -List` をログに残すフォールバックを持つ。単一 .ps1 には `tebunko.bat` に相当する起動口が無いため、この役割（印を消す・実行ポリシーを指定する・窓を隠す）は持たない。単一 .ps1 では自分自身の印（Zone.Identifier）を消す動きもしない（動き始めた後に消しても起動には効かず、EDR からは防御の回避に見えるため）。右クリック［PowerShell で実行］相当のコマンドで直接実行したときの結果は下の G6 にまとめる。
- **P7 PowerShell 5.1 のクラスの型解決**: 1 本にすると全クラスが `Add-Type -AssemblyName` より前に解析されることへの懸念があったが、結合した試作ファイル（約 1.37MB、クラス定義を含む 9 本のファイルを連結）が G1 でパーサーの構文エラー 0 件・実際の起動まで確認できたことから、この試作の範囲では問題が起きなかった。`using assembly` を先頭に置く代替案は不要だった。
- **P8 `GetNewClosure()` したスクリプトブロックからの名前解決**（`ui/index_tab.ps1` が注意する入れ子の呼び出し）: G1・G2 で画面を一通り操作した範囲ではエラーは出ていない。
- **P9 画面の開き直し**（`gui.ps1` → `IndexingSession` の `& $indexerPath`（`indexer.ps1`） を呼ぶ箇所）: P2 と同じ設計（`getPartLoad indexerLib`）で解決した。試作では結合ファイル自身を `-Part indexer` で呼ぶ形にし、10 ファイルの小規模データで 10/10 済・0 失敗の取り込みが完了することを確認した（G2・G3(c) の計測もこの経路を使っている）。

## 試作の結果

**環境**: Windows 11 Home（build 10.0.26200）、PowerShell 5.1.26100.9549、Microsoft 365（ビルド 16.0.20430.20092、x64）、論理プロセッサ 4・メモリ 8GB の仮想マシン、2026-10-02。

| 関門 | 内容 | 結果 |
|---|---|---|
| G1 | 構文と型 | 通過。結合した試作スクリプト（約 1.37MB）をパーサー（`[System.Management.Automation.Language.Parser]::ParseFile`）で構文エラー 0 件を確認し、実際に起動して画面（タイトル「tebunko」）が応答する状態で開くことを確認した。起動エラーの記録ファイルへの新規書き込みも無かった |
| G2 | 別スレッド | 通過。`-Part` 引数での自己 dot-source の切り替え（`lib`／`indexerLib`／`indexer`）が、同期実行・バックグラウンドの取り込みスレッド（RunspacePool、Workers=2）の両方で正しく動くことを確認した。`tests/testdata/` の `.docx`・`.pptx` を 10 ファイル取り込んでインデックスのファイルができ（10/10 済・0 失敗）、検索も当たった。`多数スライド.pptx` を 5 ファイル含む索引に対し「スライド」で検索すると **500 件**（切り詰め無し）が当たることを確認した（「いろはにほへと」は出現数が多く、切り詰めの上限 10000 件に達した） |
| G3 | 速さ | 不合格。下の内訳のとおり、(a) 起動が明確に不合格（複数回測り直して確認）。(b) は合格、(c) は数値上は合格の範囲だが判定保留 |
| G4 | 安全性の検査 | 通過。`tests/meta/safety.Tests.ps1` が禁止する `Invoke-Expression`・`iex`・`[ScriptBlock]::Create`・`FromBase64String`・`EncodedCommand`・`ExecutionPolicy Bypass` は、結合後のスクリプトに 0 件 |
| G5 | Defender | 通過。リアルタイム保護・AMSI が有効な状態で、ダウンロードした印（NTFS の代替データストリーム `Zone.Identifier` に `ZoneId=3` を設定）を付けた結合ファイルに対し、実際に実行したコマンド `& "$env:ProgramFiles\Windows Defender\MpCmdRun.exe" -Scan -ScanType 3 -File <結合ファイルのパス>` で静的検査を行い、検知 0 件（`found no threats`）を確認した。続けて同じ印付きファイルを `powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File <結合ファイルのパス>` で実際に実行し（取り込み 10/10 済・0 失敗）、実行前後の時刻で `Get-MpThreatDetection` を確認したところ、実行開始より後の検知は 0 件だった |
| G6 | 実行のしかた | 通過（条件は「画面が開き、多重起動の判定が働く」こと）。2 つ目の起動を試したところプロセスは 1 つだけ残り、多重起動の判定が働くことを確認した。窓の見え方・プロセスの実行ポリシーは関門にしていないが、結果として次を確認した: この仮想マシンには `.ps1` の右クリックメニューに［PowerShell で実行］の項目が無く（レジストリに `Microsoft.PowerShellScript.1\Shell\0\Command` が無い。このマシン固有の状態で、一般の Windows でも同じとは限らない）、代わりにその項目がある環境での既定のコマンド形 `powershell.exe -File "<結合ファイルのパス>"`（実行ポリシーを指定しない形）を直接実行して代用した。`tebunko.bat` を経由しないこの起動では窓（タイトル「tebunko」）が残り、起動したプロセスの実行ポリシーの実効値（`Get-ExecutionPolicy` の戻り値）は `Bypass` だった。ただしこれは、この試験環境（自動化ツールが自分自身のホストプロセスを `-ExecutionPolicy Bypass` で起動しており、環境変数 `PSExecutionPolicyPreference=Bypass` が子プロセスに引き継がれる）に由来する値であり、一般の Windows・この仮想マシンそのものの既定（`CurrentUser` スコープは `RemoteSigned`）を表すものではない |

**G3（速さ）の測り方**: zip 版と試作のそれぞれについて `powershell.exe -NoProfile -STA -ExecutionPolicy RemoteSigned -File <入口>` で毎回新しいプロセスを立ち上げ、ウォームアップ 1 回を捨てたあと 5 回測って中央値どうしを比べる。**試作の中央値が zip 版の中央値の 1.2 倍以内**なら合格とする（[速さの回帰テストと上限の決め方](../testing/perf-check.md) の「Office を使う形式の比べ方」と同じ余裕の取り方）。

| 項目 | zip 版（中央値） | 試作（中央値） | 比 | 判定 |
|---|---|---|---|---|
| (a) 起動 | 2790 ms | 18162 ms | およそ 6.51 倍 | **不合格**（1.2 倍を大きく超える） |
| (b) 最初の検索（新規プロセスの 1 回目の検索） | 1434 ms | 1292.3 ms | およそ 0.90 倍 | 合格 |
| (c) インデックス作成（100 ファイル・`.docx` 50／`.pptx` 50、読み取りスレッド 2） | 186.48 秒（参考値、下の注記） | 164.26 秒（参考値、下の注記） | およそ 0.88 倍 | 判定保留（下の注記） |

- (b) は「まっさらなプロセスを起動した直後の最初の検索」を、ウォームアップを含む 6 回すべてを毎回新規プロセスで測って比べた（本体の読み込み・検索スレッドの立ち上げの費用を、その 1 回の検索の時間に含めるため）。中央値は zip 1434 ms・試作 1292.3 ms。
- (a) の測り方: 画面を開くときに `Add_ContentRendered` で経過ミリ秒を記録する同じ 1 行の計測コードを zip 版・試作の両方に仕込み、「ウォームアップ 1 回を捨てたあと、新しいプロセスを毎回 1 から起動して 5 回測る」という同じ手順で測った。5 回の値は次のとおり。
  - zip 版: 2263 / 2356 / 2790 / 3304 / 3441 ms（中央値 2790 ms、範囲 2263〜3441 ms）
  - 試作: 14426 / 16764 / 18162 / 18572 / 19350 ms（中央値 18162 ms、範囲 14426〜19350 ms）
  - 比（中央値どうし）はおよそ 6.51 倍で、1.2 倍を大きく超える。原因の切り分け（結合ファイルの大きさ・アイコンのリテラル・自己参照 dot-source の構文解析のどれがどれだけ効いているか）は、任意のコミットを交互・反復で測れる場所（公開リポジトリ `hsgwa/tebunko-perf`）で、必要になった時点で行う。
- (c) は、取り込みのスレッドが 2 つ以上になるデータ（100 ファイル・`.docx` 50／`.pptx` 50）で測った。5 回の値は次のとおり（ウォームアップ 1 回は除く）。
  - zip 版: 190.64 / 186.74 / 134.96 / 186.48 / 118.41 秒（中央値 186.48 秒）
  - 試作: 176.53 / 200.82 / 158.3 / 149.01 / 164.26 秒（中央値 164.26 秒）
  - 比はおよそ 0.88 倍で 1.2 倍以内だが、**取り込み件数を計測後に検証できなかった**ため判定は保留とする。G3(a) が単独で不合格のため、この保留は下の「結論」の判断には影響しない。
- 計測時の注意（再現する人向け）: PowerShell 5.1 の `Get-Content -Raw`（`-Encoding` 省略）は、BOM の無い UTF-8 ファイルに日本語が入っていると既定のコードページで読んでしまい、文字化けする。結果の JSON を読むときは `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)` のように明示する。

## 自己展開型との比べ

検討の初めに、1 本の実行ファイル・自己解凍アーカイブとして配り、実行時に元のフォルダ構成へいったん展開してから動かす「別の配布の形の案」も候補にあった。今回の検討では、**展開せずに 1 本の `.ps1` のまま動かす案だけ**を試作・計測の対象にし、自己展開型そのものの作り込みは範囲に含めていない。自己展開型の試作は行っていないため、下の比べは考え方のうえでの比べ（展開せずに動かす案は試作で確かめた事実、自己展開型は一般的な性質からの推測）であり、実測ではない。

7 つの観点ごとに比べる。

| 観点 | 展開せずに動かす案（本書で試作） | 自己展開型（未試作・推測） |
|---|---|---|
| 書き込むファイル | 書き出さない。結合した `.ps1` 1 本だけが存在し、実行時にディスクへコードを展開しない | 実行時に元どおりの複数ファイル構成をどこか（一時フォルダなど）へ書き出す。書き出し先の後片付け・権限の設計が要る |
| 更新のしかた | 新しい `.ps1` 1 本を配り直すだけ。入れ替え・戻しの処理は不要 | 新しい自己解凍アーカイブを配り直す点は同じだが、**展開先に前の版の残骸が残っていないかの確認**（入れ替え・戻しの処理）が追加で要る |
| 実行ポリシーの残り方 | G6 で確認したとおり、`tebunko.bat` を経由しない起動では `Bypass` のまま残る。この点は元の複数ファイル構成と変わらない | 展開後に複数ファイルとして実行するため、展開後の起動のしかた次第（展開後に `tebunko.bat` 相当を経由するかどうか）で、展開せずに動かす案と同じかどうかが決まる。試作していないため未確認 |
| EDR・AMSI の見え方 | G5 で確認したとおり、結合した 1 本の大きな `.ps1`（約 1.37MB）をそのまま静的検査・実行時の AMSI 検査にかけて検知 0 件だった。スクリプトブロックのログ（`ScriptBlockLogging`）には、この 1 本の大きな内容がまとめて記録される | 展開の動き（自分自身を書き出して別プロセスで起動するような自己解凍の実装）自体が、EDR からは「スクリプトが新しいスクリプトを書き出して実行する」動きに見えやすく、展開前のアーカイブ本体と展開後の個々のファイルの両方が検査の対象になる。どちらが見え方として有利かは、自己解凍の実装のしかた次第で変わり、試作していないため未確認 |
| コード署名との相性 | 署名する対象は結合ファイル 1 本だけで済む。WDAC などで信頼させる場合も、対象が 1 つなので運用しやすい | 自己解凍アーカイブ本体に署名しても、展開後の個々のファイルは署名が検証されない（展開のしかた次第）。WDAC で展開後のファイルも信頼させるには、別途の仕組みが要る |
| `scripts\` の作りへの影響 | 上の「パスに頼っている所」（P1〜P9）のとおり、`scripts/` 配下のソースを 1 本化を前提にした形へ書き換える必要がある。変える量は P1〜P9 の広い範囲に及ぶ | 展開が終わったあとは今までの複数ファイルの前提がそのまま使えるため、`scripts/` 側の書き換えは展開せずに動かす案より少なく済むと見込まれる（自己参照の dot-source の保守負担が生まれない） |
| 制限言語モード・AppLocker での動き | tebunko.bat のフォールバックが `$ExecutionContext.SessionState.LanguageMode` をログに残す仕組みを確認したが、制限言語モードや AppLocker のポリシーそのものを変える効果は無い。1 本化してもこの点は変わらない | 展開のしかた次第で、自己解凍の実行ファイル自体が AppLocker のルール（実行ファイルの署名・パスのルールなど）の対象になりうる。試作していないため未確認 |

展開せずに動かす案は「自己参照の dot-source を保守し続ける負担」（上の「パスに頼っている所」）を新しく抱える代わりに、書き込むファイルが無く、署名・EDR の対象が 1 本で済むという利点がある。自己展開型は `scripts/` 側の書き換えが少なく済む代わりに、展開そのものに別のリスク（展開失敗時の挙動・一時フォルダの権限・EDR からの見え方）を抱える。どちらも「1 本のファイルで配る」という利用者から見た見た目は同じになりうるが、保守の負担の種類が異なる。今回は前者だけを試作・計測した。

## 層とテストへの影響

- 1 本化は `scripts/` のソースを連結するだけで、[ソースの分け方](source.md) の判断層・状態層・画面層の区別や依存の向きそのものは変えない。層の決まりを検査する `tests/meta/` の既存のテストは、結合前のソース（複数ファイルのまま）に対して動くため、1 本化そのものはこれらのテストの対象や合否に影響しない。
- 影響が出るのは、結合という**新しい工程**を実運用に組み込んだ場合。試作で使った自己参照 dot-source の方式は、結合ツールが機械的に書き換える箇所が増えるたびに書き換えを追従させ続けなければならず、今の `tests/meta/` のどの検査にも対応するものが無い（上の P2 を参照）。実運用に進める段階 1 では、別スレッドが単一 .ps1 そのものを自己 dot-source しない設計に改め、この種の書き換え漏れが構造的に起きない形にした。
- 速さの計測（G3）についても、[速さの回帰テストと上限の決め方](../testing/perf-check.md) の既存の仕組みは複数ファイルの今の配布物を対象にしており、結合後のファイルは測っていない。1 本化を続けるなら、結合後のファイルも同じ仕組みで継続的に測れるようにする必要がある。

## 結論

計画で決めた判定の規則は「6 つの関門が全部通れば進める・1 つでも通らなければ進めない」。G1・G2・G4・G5・G6 は合格したが、**G3（速さ）の内訳 (a) 起動が明確に不合格**（zip 版の中央値 2790 ms に対し試作は 18162 ms、およそ 6.51 倍。1.2 倍の上限を大きく超える）。

この規則どおりなら「進めない」という判断になるところ、2026-10-03 にメンテナが実装を進める判断を下した。G3(a) の不合格はマージの条件にせず、測った倍率と秒数を試験版の説明に書いたうえで、**起動の速さが zip 版の 1.2 倍以内になるまでは「試験版」として、zip 版と並べてリリースに載せる**（一気に置き換えない）。その後、実装版で起動を測り直したところ zip 版の約 0.97 倍に収まった（下の「実装版での起動の測り直し」）。出すかどうかの最終判断は、メンテナの動作確認で行う。

- G3(c)（インデックス作成）は数値上は 1.2 倍以内に収まったが、取り込み件数を確かめる仕組みがこの回の計測でうまく働かず、判定を保留した（上の G3 の内訳を参照）。試験版として出す判断には影響しない。
- 自己参照 dot-source の構造的な負担（上の P2）は、下の「入れた段階」の段階 1 で、別スレッドが単一 .ps1 そのものを自己 dot-source しない設計に改めることで解消した。

## 実装版での起動の測り直し

実装した結合の道具（`tools/new_single_script.ps1`）で作った単一 .ps1（約 2.0MB）と、同じコミットの `scripts\`（zip 版）の画面が開くまでを、同じ機械（試作のときと同じ仮想マシン）で、`powershell.exe -NoProfile -STA -ExecutionPolicy RemoteSigned -File <入口>` から測り直した（2026-10-04）。ウィンドウのタイトル「tebunko」が現れるまでの経過ミリ秒で、zip 版と単一 .ps1 を入れ替えながら 2 巡し、各巡のウォームアップ 1 回を除く 4 回ずつ（合わせて 8 回ずつ）を比べた。測っている間、ほかのプロセスの負荷で CPU 使用率は 57〜74% あり、値は試作のときの測りより大きい。

| | 値（ms） | 中央値 |
|---|---|---|
| zip 版 | 4174, 3438, 3185, 3751, 5417, 4167, 4290, 3687 | 3959 |
| 単一 .ps1 | 3386, 2884, 3169, 4486, 4366, 4333, 4597, 3166 | 3860 |

比はおよそ 0.97 倍で、1.2 倍以内に収まった。試作のときの約 6.51 倍から変わった理由（自己参照の dot-source をやめ、部品を文字列で持って読む形にしたこと）の切り分けは行っていない。測りは負荷のある機械での 8 回ずつで、ばらつきが大きい（zip 版は 3185〜5417 ms）。(b) 最初の検索と (c) インデックス作成は、実装版では測り直していない（試作のときの値のまま）。

## 入れた段階

計画段階で決めた 3 つの段階で実装した。

1. **`refactor`: 画面と別スレッドが部品をパスで読まないようにする。** 上の P2〜P5 に挙げた、別スレッドがパスで部品を読む箇所・パスに頼る基準（`$rootDir` など）を、1 本化を前提にした形へ書き直した。zip 版の動き（複数ファイルのまま）は変えない。別スレッドへの部品の渡し方は `scripts/tebunko/core/parts.ps1` の `getPartLoad` に 1 か所へ集め、`tests/meta/structure.Tests.ps1`・`tests/meta/layers.Tests.ps1` に 1 本化を見越した決まりを足した。詳細は [クラスと関数の使い分け](classes.md)・[プロセスとスレッド](threads.md)・[ソースの分け方](source.md)。
2. **`build`: 結合した 1 本の `.ps1` を作る道具と、その検査を作る。** 試作の結合ツールを、使い捨てではなくリポジトリで保守する道具 `tools/new_single_script.ps1` に作り直し、連結の順・構文・禁止の語・部品の過不足を機械的に確かめる検査を添えた（読み込みのたどり方と禁止の語の一覧は `tools/script_rules.ps1` に集め、`tests/meta/layers.Tests.ps1`・`tests/meta/safety.Tests.ps1`・`tools/check_release_package.ps1` と共有する）。`release.yml` で結合後のファイルを作り、zip 版と並べて配布物として公開する（単一 .ps1 そのものはリポジトリにコミットしない）。
3. **`docs`: README・利用者の手引き・安全性の説明に、1 本の `.ps1` の形を足す。** README に、ダウンロードから右クリック［PowerShell で実行］までの使い方・実行ポリシーの注意・設定とインデックスの置き場・試験版の扱い・zip 版との間のエクスポート/インポートでの移し方を足した。[配布物と開発用のフォルダ構成](folders.md)・[ファイルの読み書きの範囲](../../safety/file-access.md)・[開示事項](../../safety/disclosure.md)・[第三者のツールによる検査結果](../../safety/scans.md) に、単一 .ps1 の扱いを足した。[ソースの分け方](source.md)・[プロセスとスレッド](threads.md) にも、結合の元が変わらないことと、別スレッドの部品の読み方が zip 版と同じ形になることを足した。

実装版の起動は zip 版の 1.2 倍以内（上の測り直し）だが、(b)(c) の測り直しと利用者の確かめが済むまでは「試験版」の扱いとし、[速さの回帰テストと上限の決め方](../testing/perf-check.md) に相当する形で結合後のファイルの速さを継続的に測れるようにする。
